# M322 — `main` at 0x80000520: 30 of 30, and a retraction the root view earned

The function was `main` — the boot initialiser — and it is byte-exact on the first draft. The interesting part is
what the attempt corrected: a claim I made in M320 and M321 about this very address, and a defect in the tool that
made the claim.

## 1. The function

```c
void FUN_x(void)
{
    u32 *p = __bss_start;              /* 0x800138A0 */
    u32 n = __bss_end - __bss_start;   /* 0x80018A80 -> 21632 words */

    while (n--)
        *p++ = 0;
    FUN_800004f0(0);
    FUN_800070c0();
    while (*(u32 *)0x80000300u == 0)
        ;
    FUN_80000598();
}
```

**30 of 30 words**, one draft after two corrections — and both corrections are about *reading*, not writing:

- **`__bss_end` is `0x80018A80`, not `0x80028A80`.** The image's `lui v0,0x8002; addiu v0,v0,0x8a80` uses a
  **sign-extended** immediate, so it computes `0x80020000 − 30080 = 0x80018A80` — which is exactly the **stage-2 load
  address**, i.e. the end of the boot image. So the cleared region is the boot's own tail, `0x800138A0..0x80018A80`.
  Reading the immediate as unsigned (as `sw` displacements are) gave a plausible but wrong address, and that one
  error accounted for 9 of the first draft's 11 misses.
- **the spin is `while (*(u32 *)0x80000300u == 0) ;`** — five variants tried; `for(;;)` and `do{}while(1)` produce an
  unconditional self-jump (`j`, with a `nop` filler), while the image has a **conditional** self-branch with
  `addu v0,zero,zero` in the `bne` delay slot. Only the `while (flag == 0)` form produces that pair.

This is the corpus's first **named** function to become byte-exact while staying named (`main`, from
`config/symbols.tsv`): the ladder's F3 rung and its byte-exactness now coincide in one entry.

## 2. The retraction

**M320 and M321 both said `0x80000520` "is not a census function start at all". That is wrong**: the index lists it
as `main`, 30 words, `status: written` — it was *correct all along*. The claim came from `leaf_screen --called`,
whose walk reported `boot:0x80000518` as `2w -> 32w`: the walk started at `idle_spin`, a two-word `b .` that never
returns, and ran **straight through it into `main`'s body**, reporting another function's extent as its own.

Fixed: the walk now stops at a self-branch (`beq $0,$0,-1` or a self-targeting `j`) and reports
*"never returns: self-branch"* instead of an extent. The truncated-extent set is therefore **five**, not six —

| image | address | census | true | callers |
|---|---|---|---|---|
| stage2 | `0x8004276c` | 3 w | 46 | 96 |
| stage2 | `0x80042824` | 3 w | 46 | 20 |
| boot | `0x80000dd4` | 5 w | 95 | 7 |
| stage2 | `0x800421b4` | 3 w | 46 | 3 |
| boot | `0x800115b0` | 3 w | 5 | 1 |

and `0x80000518` is a correctly-bounded 2-word `idle_spin`.

## 3. What the shape of this was

M320 read the corpus from the **roots** — references, callers, extents — and found five bodies far larger than the
index said. M321 read the same five from the **canopy** — instructions, opcodes, what a compiler can emit — and found
four of them are not C. Here the root walk itself was wrong in one place, and the canopy measurement (30 words,
byte-exact) is what exposed it.

The two views only agree when they are read through the same trunk, and the trunk is the **extent**: the one number
both the call graph and the body have to name. Every time this project has grown, it has grown where the two
disagreed — and at least twice the disagreement was in the *reading*, not in the game. That is the whole method in one
sentence, and it is why the retraction belongs in the same note as the win.
