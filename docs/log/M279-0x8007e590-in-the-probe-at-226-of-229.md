# M279 — `0x8007e590` enters the probe at 226 of 229, as a *partial* pin with a regional assertion

The instruction was to park case 4's three words and register the function anyway. This is that: the reconstruction
now lives in `tools/compile_probe.py` as `P7E590_SOURCE` with two cases of its own, the acceptance pin moved
**30 → 32**, and the progress map grew a second `▓` cell.

## 1. Why a partial belongs in the probe at all

The corpus's rule is that a case asserts a *fact about the build*, not that a function is finished. `p8` set the
precedent at M266 — 136 of 139 words with an itemised three-word residue — and the reasoning there holds here
unchanged: a partial that is **measured and pinned** keeps the work reproducible and catches regressions, while a
partial that lives only in a note rots the moment the next target changes the struct or a flag. The alternative,
leaving `0x8007e590` unregistered until it is exact, has already cost this project one thing worth naming: M275's
"95 of 229" and M277's "176 of 229" were both checked by a harness in `build/`, which is gitignored — so neither
number could be re-derived by CI, and both were re-measured by hand from a scratch script.

## 2. What the two cases assert, and why the second one is not redundant

```python
bool(p7e590f) and p7e590f["same_offset"] >= 226 and p7e590f["case3"] == 113
bool(p7e590f) and p7e590f["table_same"] == 6
```

Three deliberate choices:

- **`>= 226`, not `== 226`.** The pin must fail on a regression and *pass on an improvement*; an equality pin would
  turn the next session's progress into a gate failure, which is exactly the direction the corpus should never punish.
  `p8`'s `same_offset >= 136` is the precedent, and it is a `>=` for the same reason.
- **`case3 == 113` is the assertion that matters.** A whole-function pin at 226 is satisfied by *any* arrangement of
  226 identical words, including one where the 113-word arm loses ten and the head gains ten. The arm is pinned
  exactly (113 of 113), so the structure this session verified cannot silently decay into a different 226. This is the
  same argument the per-region tables in M275/M277/M278 were built on, moved into the gate.
- **The jump table is its own case**, 6 of 6 words at `0x800b9c78`, with the sixth word zero because the switch's
  bound is 5 — the table is placed by the linker script rather than found by the source, so it is a claim about the
  toolchain and would fail independently of the code.

## 3. The number that moved, and the ones that followed it

Two new cases move the corpus to **32 cases, all passing**, and the derived counts follow: the verification suite is
**72 suites / 1001 cases** (from 999), of which **721 need the cartridge** (from 719), with the runnable tiers
unchanged at 31 suites / 280 cases. Those numbers appear in five places — `README.md` twice, `docs/handover.md` twice,
`tools/ci.sh`, and `.github/workflows/acceptance.yml` three times — and all six were moved through
`tools/patch_text.py` with unique anchors, which then verified each file after writing. The progress map re-rendered
with a second `▓`: **6 reproduced byte-for-byte, 2 recovered with the residue itemised**.

## 4. What the function's presence now says

`0x8007e590` is the largest function in the corpus by a wide margin — 229 words against `0x80059530`'s 206 — and it is
the first entry whose residue is a *structural* discovery rather than a shape one: the switch has no `default:`, so
case 3 `break`s into the device-update tail while case 1 and case 4 `return` past it, and getting that wrong costs
exactly three words per arm in a `void` function where `break` and `return` behave identically. Registering it means
that fact is now asserted rather than described: if a future change to the compiler patch level or the flag set
breaks the tail's placement, the case fails and names the arm.

The three unclaimed words stay unclaimed in the prose as well: the README's row reads "226 of 229" with the residue
named (`li a0,5` where the image has `li v0,5`), the progress map entry says "229 words, 226 exact: three words, one
register in case 4's select", and the note that produced it (M278) is where the fifteen refuted variants are listed.
Nothing here is admissible beyond that: `verify.py --full` was not run, so the gate audit has not graded itself
against the new pin.
