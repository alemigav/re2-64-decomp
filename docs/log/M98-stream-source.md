# M98 — where the stream comes from: a runtime buffer inside the room overlay

The chain from `FUN_8003287c` up to its data source is now complete, and it ends in RAM, not in the
cartridge. Six hops, five of them static.

## 1. The chain

```
FUN_8006d8f0  (the driver)
  s0 = 0x800c76b0 + 0x18000 = 0x800df6b0        ; the same base the bank initialiser used (M84)
  v0 = lw 0x27c(s0)                              ; *(0x800df92c) = the script structure
  v0 = lw 0x48(v0)  /  lw 0x4c(v0)               ; two stream pointers
  sw v0, 0x145c(ctx)                             ; stored into the context
  jal  FUN_8006da14                              ; run the command loop
        └─ lw ctx+0x1c → lbu byte0 → table[141 @ 0x80113898] → jalr
              └─ handler FUN_80071e14 → lbu byte3 → FUN_8003287c(slot)
```

So `ctx+0x1c` (the "descriptor") is a **command** in a stream, and the stream pointer ultimately comes
from `*(0x800df6b0 + 0x27c)`, which I will call the **script structure** pointer.

## 2. Who sets it — two writers, two flavours

`*(0x800df92c)` is written from exactly two sites in 36 images:

**Writer 1 — the overlay, `ovl_007c552` at `0x8016ea70`, in `FUN_8016e8d0`:**

```
0x8016ea60  lui   v1,0x8017
0x8016ea64  lw    a0,644(s0)        ; *(0x800df934) — a scene/heap pointer
0x8016ea68  addiu v1,v1,0x1df8      ; v1 = 0x80171df8
0x8016ea6c  sb    zero,6(v1)
0x8016ea70  sw    v1,636(s0)        ; *(0x800df92c) = 0x80171df8   <- THE STREAM
0x8016ea74  sw    a0,8(v1)
```

**Writer 2 — stage-2, `0x80063698`, in `FUN_800635b0`:** `lw a0,0x280(s0)` then
`sw a0,0x27c(s0)` — a heap pointer, i.e. a dynamically built command list.

So the interpreter serves both a **fixed buffer address** and a **heap-built list**. That is why the
command pointer has two advance flavours (M97's `+2` path and the `addu a1,a1,t0` path).

## 3. The buffer is empty in the cartridge

`0x80171df8` is inside `ovl_007c552`'s RAM window: the overlay loads at `0x8016e880`, is 15 104 B, so
its static content ends at `0x80172380`, and `0x80171df8` is at **overlay offset `0x3578`**. Reading
that offset in `assets/unpacked/00005_007c552_15104.bin`:

```
+0000  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
…      (all zero for the first 96 bytes, and the opcode histogram over 2 KB of 4-byte
        "commands" has exactly one entry: 0, 354 occurrences)
```

**Zero.** It is a BSS workspace, and the commands are placed there at runtime by the overlay's own
code — `FUN_80170104` and `FUN_801708a4` read and write through `0x80171e80`, inside the same buffer.

## 4. What that settles, and what it ends

* **The slot values are not shipped data.** They are byte 3 of opcode-`0x44` commands that do not
  exist until the room overlay generates them. Reading the cartridge cannot enumerate them, and every
  static route is now exhausted — not assumed, but traced to a buffer that is provably zeros on disk.
* **The interpreter belongs to the room overlays, not to stage-2.** The stream is created by the
  overlay; the shared stage-2 code is the loop, the 141-entry handler table, and the ten contexts.
* **This closes the thread that began at `FUN_8003287c`.** The full path is:
  room overlay → BSS command buffer → `*(0x800df92c)` → context `+0x145c` → `ctx+0x1c` → byte 0
  selects a handler, byte 3 is the slot → `fun_8003287c` → `cart_record` → descriptor loader.

## 5. What would answer the original question now

Only execution. Two routes, both requiring the game running at a room:

1. **Dump the buffer**: with a room loaded, read `*(0x800df92c)` and the 2–4 KB at `0x80171df8` from an
   ares RDRAM export, then scan for `0x44` at the command stride. That is one dump and one scan.
2. **Watch the dispatcher**: log `a0` at `0x80071ebc` (the `lbu` of byte 3) and collect the
   distribution. The harness can do this once the contexts exist.

Neither is a disassembly question any more, which is the useful outcome: **the code path is mapped;
what remains is a data question that needs a running game.**

## 6. Recorded limitation

The buffer's internal layout is **not** established — whether commands are 2, 3 or 4 bytes, and
therefore whether byte 3 belongs to the current command or the next one. M97 flagged that the `+2`
advance and the byte-3 read are inconsistent; the fact that the buffer is generated by overlay code
(and empty in the file) means the stride can only be settled from a runtime dump or by reading
`FUN_80170104`, which is the overlay's command writer. That is the next static step if one is wanted.
